# Project Formatting and Coding Style

This repository uses the following formatting and coding conventions.

## Maven POM formatting

- Use XML declaration:
  `<?xml version="1.0" encoding="UTF-8"?>`
- Keep the `<project>` namespace declaration on the opening line and wrap `xsi:schemaLocation` on the continuation line as needed.
- Put each XML element on its own line.
- Put each child element of `<parent>`, `<properties>`, `<dependency>`, and `<plugin>` on its own line.
- Do not combine sibling XML elements on one line.
- Use four spaces for XML indentation.
- Keep dependencies and plugins vertically readable.
- Keep `<build>`, `<plugins>`, and `<plugin>` nested with four-space indentation per level.

Example:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

## Java formatting

- Use four spaces for indentation; do not use two-space Java indentation.
- Keep imports grouped and separated by a blank line:
  1. project imports;
  2. Java standard-library imports;
  3. framework/library imports.
- Keep one field declaration per line.
- Keep constructors readable. Wrap long parameter lists one parameter per line.
- Wrap long method calls and chained calls vertically.
- Wrap long `return`, `throw`, query, and lambda expressions rather than allowing very long lines.
- Keep annotations directly above the class, field, or method they annotate.
- Use braces consistently for conditionals, including single-statement blocks.
- Format entity builders with one field assignment per line.
- Match the formatting style of `inventory-service/src/main/java/com/example/inventory/service/InventoryServiceImpl.java`.

## Lombok scope

- Use Lombok only on JPA entity classes.
- Do not use Lombok on controllers, services, service implementations, filters, configuration classes, or other application classes.
- Entities may use class-level:
  - `@Data`
  - `@NoArgsConstructor`
  - `@AllArgsConstructor`
  - `@Builder`
- Entity constructors should be generated by Lombok; do not add separate manual constructors.
- Entity creation in application code and tests should use builders so field names are explicit.
- No protected constructor access is required for these entities.

## Entity builder style

Use:

```java
User.builder()
        .userId(userId)
        .username(username)
        .passwordHash(passwordHash)
        .role(role)
        .createdAt(createdAt)
        .updatedAt(updatedAt)
        .build();
```

## Service and controller constructors

- Services, service implementations, controllers, filters, and configuration classes use explicit constructors.
- Do not apply Lombok constructor annotations outside entities.
- Keep service interfaces separate from `*Impl` classes.

## Exception policy

- Custom application exceptions must extend `Exception`, not `RuntimeException`.
- Service and controller method signatures must explicitly declare checked application exceptions they can throw.
- `ControllerAdvice` remains responsible for mapping checked application exceptions to HTTP responses.
- Any checked exception thrown from a `@Transactional` method must be included in the transaction rollback configuration, for example `@Transactional(rollbackFor = ApplicationException.class)`.
- Do not hide checked application exceptions by wrapping them in generic runtime exceptions.
- Background workers and Kafka consumers must handle checked application exceptions locally because no HTTP `ControllerAdvice` request is active.
